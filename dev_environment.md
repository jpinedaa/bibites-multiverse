# Developer guide and technical findings

This guide explains how to build, test, and inspect Bibites Multiverse.
It also keeps durable findings from the development rigs.

This file is not a live deployment record. It does not contain current service health,
resource inventory, costs, credentials, private addresses, incidents, or rollout receipts.

## Layout

| Area | Path | Purpose |
|---|---|---|
| Game plugin | `bibites-mod/` | BepInEx and Harmony source, build scripts, and local game controls |
| Plugin references | `bibites-mod/libs/` | Gitignored game and BepInEx assemblies |
| Decompiled game source | `decompiled/BibitesAssembly/` | Gitignored API reference generated by `ilspycmd` |
| Go module | `go/` | Relay, sidecar, archive, diagnostics, and protocol tests |
| Protocols | `contracts/` | Versioned Contract A, Contract B, and genome identity rules |
| Test rigs | `e2e/` | Multi-world tests, failure rehearsals, and evidence tools |
| Participant packages | `release/` | Release assembly, the release checks, and install or uninstall tests |
| Private far-end kit | `farend/` | On-demand Windows bundle builder and setup scripts for a private test map |
| Participant guides | `docs/` | Install, join, diagnose, leave, defaults, and support data |
| Deployment code | `deploy/` and `cloud/aws/` | Reusable public-service and cloud-world implementation |

Runtime data stays outside Git. This includes saves, journals, logs, credentials, build output,
game files, captures, and archive data.

### Working copies on the development machine

Most work happens in a `git worktree` beside the main checkout. A worktree is a working copy, not
a record: everything it holds is either committed or not worth keeping.

Remove a worktree when its branch is merged. Confirm the branch first, then remove the directory
and the branch:

```sh
git merge-base --is-ancestor <branch> origin/main   # must exit 0
git worktree remove <path> && git worktree prune
git branch -d <branch>                              # -d only; never -D
```

Do the same for a merged remote branch that has no open pull request. Keep an unmerged worktree,
a worktree with uncommitted changes, and the divergent branches that are preserved on purpose.

Do not keep a checkout of an old deployed commit as a staging copy. `git clone` and
`git checkout <sha>` rebuild one in seconds, and a stale copy is indistinguishable from current
source at a glance.

## Workflow

### Prerequisites

The plugin workflow needs these local inputs:

- A supported game installation.
- BepInEx in that game directory.
- A .NET SDK that can build .NET Standard 2.1.
- `ilspycmd` for the generated decompile.
- WSL for the included Windows game-control scripts.

The Go workflow needs only the Go version in `go/go.mod`.
Do not commit any copied game assembly or decompiled game file.

### The reference DLL set

Run this command after a game update:

```sh
bibites-mod/sync-game-refs.sh
```

The script copies 13 reference assemblies into `bibites-mod/libs/`.
It also regenerates `decompiled/BibitesAssembly/` and writes `libs/.sync-stamp`.

The managed set contains these assemblies:

- `BibitesAssembly.dll`
- `Newtonsoft.Json.dll`
- `Newtonsoft.Json.UnityConverters.dll`
- `ShapesRuntime.dll`
- `UnityEngine.dll` and the required Unity modules

The script also copies `0Harmony.dll` and `BepInEx.dll` from BepInEx.

The quick freshness check compares only `BibitesAssembly.dll`.
Use `sync-game-refs.sh --force` after the reference list changes.
If the build cannot resolve a listed assembly, use the force option.

After every game update, review changed APIs and rerun the M1 exit test.
The game can change an API without changing this repository.

### Build and deploy the plugin

Build without copying into the game:

```sh
dotnet build bibites-mod/BibitesMultiverse.csproj -c Release
```

Build and copy the plugin into the local Steam installation:

```sh
bibites-mod/game.sh stop
bibites-mod/deploy.sh
```

Stop the game first. Windows locks the loaded plugin DLL.
The build can succeed although the final copy fails.

### Run the plugin auto-test

The M1 auto-test loads its own world, completes a round trip, saves, and exits.
It does not use another world.

```sh
WSLENV=MULTIVERSE_AUTOTEST \
  MULTIVERSE_AUTOTEST=1 \
  bibites-mod/game.sh start
```

Use the log command to read the result:

```sh
bibites-mod/game.sh log main 120
```

Wait for `[M1-AUTOTEST] RESULT: PASS`.

### Fast Go loop

The Go tests do not need the game:

```sh
cd go
go build ./...
go test ./...
go test -race ./...
gofmt -l .
go vet ./...
```

`gofmt -l .` and `go vet ./...` must print no findings.

Build static local binaries from the repository root:

```sh
cd go
CGO_ENABLED=0 go build -o ../bin/ ./cmd/...
```

Build the Windows sidecar:

```sh
cd go
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
  go build -o ../bin/multiverse-sidecar.exe ./cmd/sidecar
```

A running process can lock its binary. Build into a temporary path before a controlled
replacement, or stop the process before an in-place build.

### Control local game processes

`bibites-mod/game.sh` controls each Windows game by its recorded process identifier:

```sh
bibites-mod/game.sh start A
bibites-mod/game.sh status
bibites-mod/game.sh logfile A
bibites-mod/game.sh log A 60
bibites-mod/game.sh wait A 60
bibites-mod/game.sh stop A
```

Start a headless game with Unity's own flags:

```sh
BIBITES_EXTRA_ARGS='-batchmode -nographics' \
  bibites-mod/game.sh start A
```

The script maps an instance to a BepInEx log by content.
It never assumes that start order selects a log name.

WSL forwards only environment variables that `WSLENV` names.
Name every `MULTIVERSE_*` variable that the Windows game needs.

### The M4 rigs — `run-m4.sh` and `run-m4-lan.sh`

The `e2e/` scripts are evidence rigs, not public-service controls.
Read the header of a rig before you run any phase.

- `e2e/run-m4.sh` rehearses a 3-by-2 map on one machine.
- `e2e/run-m4-lan.sh` rehearses the same topology across two machines.
- `e2e/crossing/RUNBOOK.md` describes the historical protocol-major rehearsal.
- `e2e/run-m3*.sh` preserves the M3 phase structure and uses a retired wire.
- `e2e/run-m2.sh` preserves the M2 exit test and uses `contract-b/1`.

Use `--help` or the script header to find supported phases.
Do not assume that a historical rig can speak to current binaries.

Only one fixed-port rig can run in one checkout at a time.
Before you start another rig, make sure that its listeners and data paths do not conflict.

### Reading the logs — the grepable series

Mod log lines use bracketed series tags. Useful tags include:

| Tag | Evidence |
|---|---|
| `[M1-AUTOTEST]` | M1 round-trip result |
| `[M2]` | configuration, sessions, and migrations |
| `[M2-FAMILY]` | population and family-link reports |
| `[M4-SAVE]` | save duration and phase timing |
| `[M4-PORTAL]` | portal creation and visual events |

Go services use structured text fields instead of these tags.
Use `ringstat`, `worldstat`, and the service test clients for machine-readable results.

`LogOutput.log` is overwritten at each game launch.
If the prior run is test evidence, copy its log before restart.

### Driving one component by hand

Each Go command documents its own flags:

```sh
cd go
go run ./cmd/relay --help
go run ./cmd/sidecar --help
go run ./cmd/archive --help
go run ./cmd/ringstat --help
go run ./cmd/worldstat --help
```

Some Go flag parsers return exit status 2 for `--help`.
Capture the help text before you examine it in a shell pipeline.

Use temporary data directories for manual tests.
Never point a development command at a live data directory.

### The release checks

Every pull request and every push to `main` runs `.github/workflows/checks.yml` on GitHub-hosted
runners. That workflow needs no game file and no secret. It runs `go vet` for this host and for
Windows, `go test ./...`, the cross-builds the release and the hosting kit ship, `bash -n` over
every tracked shell script, `deploy/test-units.sh`, `deploy/test-front-door.sh`, a stub compile of
the Windows installer script, a PowerShell parse on Windows, and two consistency gates.

Run the two gates by hand before you push a change to the mod, the sidecar, or the release
version:

```sh
release/bump-version.sh --check
release/check-drift.sh
```

The first proves that every place naming the release agrees with `release/make-release.sh`.
The second proves that this tree is still the build that was tested, and that the plugin version
agrees across `bibites-mod/src/MultiversePlugin.cs`, both rows of `docs/support-matrix.md`,
`testedBuild.mod` in the same file, and the Plugin row of the Versions table above.
Neither needs the game, the .NET SDK, the network, or Git history.

A `v*` tag on `main` starts `.github/workflows/release.yml`.
That workflow builds and publishes the release on the owner's own machine, the only place the
proprietary build inputs exist.
Read [`release/README.md`](release/README.md) for the procedure, the runner's setup, and the
by-hand fallback.

### Owner steps

This public guide does not contain machine-specific service procedures.
For a LAN test, `e2e/run-m4-lan.sh lanhost` prints the addresses and commands from runtime data.

The LAN firewall rule and WSL port proxy must use the configured relay port.
Read [`deploy/README.md`](deploy/README.md) for reusable public-service procedures.

## Durable technical findings

These findings came from completed milestones. They remain useful after their original rigs stop.

### The save-file rotation layout

Periodic saves and save-on-quit use this layout:

| File | Meaning |
|---|---|
| `<world>.zip` | Newest verified save |
| `<world>-<yyyyMMddTHHmmssZ>.zip` | Rotated backup with a sortable UTC name |
| `<world>.partial.zip` | Unverified temporary save |
| `.multiverse-save.lock` | Cross-instance save lock |

The order is write, verification, rotation, then pruning.
Verification requires `scene.bb8scene` in the ZIP.

The old live save becomes a timestamped backup before the partial file becomes live.
The live name is absent briefly between those two renames.
Readers must retry that short absence.

A resting partial file means that a save stopped before completion.
Do not select partial files with a broad `*.zip` scan.

### Credentials, TLS, and the retired LAN token

Contract B 4 uses TLS and one credential per peer.
The relay stores credential verifiers, not credential secrets.

Contract A 2.4 uses a bearer token on the loopback connection.
The sidecar creates that token in its data directory.

The earlier shared LAN token belongs only to retired protocol versions.
Do not add it to a current test or configuration.

Never store a join string, peer secret, TLS private key, or Contract A token in Git.
Use placeholder names in examples and issue reports.

### The far end

The `farend/` directory builds a Windows artifact for a test computer without Go or .NET.
The artifact contains the plugin, BepInEx, sidecar, setup script, and start or stop scripts.
It is for a private test map. A participant on the public map uses the release installer instead.

Build the artifact when a far end needs one. Nothing in `farend/dist/` is tracked.
Carry the zip, the certificate authority, and the peer secret to that machine by hand.
Stop the old Windows sidecar before you replace its executable.

What a release build compares itself against is not this artifact.
It is the `testedBuild` record in `docs/support-matrix.md`.
Update that record after a plugin or sidecar change, with `release/record-tested-build.sh`.
`release/check-drift.sh` reports when the record no longer describes this tree.
A release build refuses a tree that the record does not describe.

The far-end scripts require an explicit relay location and a peer credential.
Those values are runtime inputs and do not belong in this guide.

The local test cannot prove that a remote operator applied a new bundle.
Use the remote peer handshake or an operator report as evidence.

### The disk budget

Bounded logs and compacted journals changed the storage shape from monotonic growth to a mix of
bounded and retained data.

The durable rules are:

- Compact sidecar journals on a timer and during replay.
- Rotate service logs by size.
- Keep each append all-or-nothing.
- Measure archive replay from the current ledger size.
- Treat genomes and the migration ledger as separate retention classes.
- Keep raw logs, saves, and captures out of Git.

The migration ledger grows for as long as records are retained.
A fixed replay-duration estimate becomes stale as the ledger grows.

### Append-only recovery

A failed append can leave a short line in the middle of a file.
Later successful appends can put valid history after that damaged line.

The sidecar journal truncates back to its old length after a failed append.
It does not acknowledge the failed record.

Journal replay treats a damaged final line as a torn tail.
Damage before later complete records is an error and reports discarded bytes.

Archive replay skips a damaged line and continues with later records.
It reports the skipped line count and byte count.

Tests for any new append-only file must cover short writes, replay, and valid records after damage.

### Archive replay and growth

Archive startup replays the complete retained ledger before it serves HTTP data.
Replay time and peak memory therefore scale with retained history.

The streamed replay reduced peak memory substantially in the M5 test data.
The exact duration remains host-specific and becomes stale.

Use the current line count and byte size for each replay estimate.
Do not copy an old number into a timeout.

An archive subscriber that is offline does not receive past migrations later.
A restart during active traffic can therefore create a permanent archive gap.
Test suites must state whether that gap is allowed.

Historical genome gaps tracked the crossing rate and drained after traffic decreased.
That result identified a throughput backlog, not a lost-record leak.

### The five-instance ceiling

BepInEx tries `LogOutput.log`, then suffixes `.1` through `.4`.
It stops creating disk logs after five game processes lock those files.

On the tested installation, a game without a BepInEx disk log did not load the plugin.
The hardware still had enough memory and processor capacity.

Use at most five real game processes in one shared game installation.
For an extra synthetic slot, use `cmd/fakemod`.
For an extra real world, use another installation.

Map each game to its log by a unique startup marker.
Do not map logs by process start order.

### A world can be at the wrong time scale

Three values describe simulation speed:

| Value | Meaning |
|---|---|
| Target | Requested game time scale |
| Applied | `Time.timeScale` after the game's governor acts |
| Achieved | Simulated-time change divided by wall-time change |

These values can differ greatly under load.
The target is not proof of simulation throughput.

`TimeController.CheckMinFPS` can reduce the applied value.
`Time.maximumDeltaTime` also limits progress to one simulation tick per rendered frame.

The plugin's headless governor option can disable the minimum-FPS servo.
It does not change the user's persisted game configuration.

Use achieved speed for performance claims.
Record population and simulation tick rate beside every speed comparison.

### Save cost and evolutionary history

World-save stalls depend more on serialized world history than on ZIP size.
The main variable is the raw evolutionary history in `speciesData.json`.

A synchronous save can exceed the old two-second test budget on mature worlds.
Measure the internal save phases before changing compression or file rotation.

In one historical sample, 50.8% of saves over 3.5 seconds preceded a heartbeat close.
Only 0.2% of saves under two seconds preceded the same close.

Headless saves remain complete, but their thumbnail is blank.
The blank PNG is smaller and can distort metrics normalized by compressed ZIP size.

### Default migration edges

An unset export-edge configuration enables all four edges.
The explicit values `none` and `off` disable the Multiverse client.

This default is part of the release contract.
Test rigs set their edge configuration explicitly to protect their measurements.

### World readiness

Do not load a world before `ProceduralSpriteManager.Instance.done` is true.
The sprite atlas builds asynchronously.

An early organism spawn can throw inside `BibiteBody.FinalizeBirth`.
The game loader can swallow that exception and return `null`.

The mod gates world loading and migration on the readiness flag.
Every new test harness must use the same condition.

### Windows directory synchronization

POSIX code often synchronizes a directory after a rename.
Windows can return `Access is denied` for that directory operation.

The shared helper under `go/internal/fsutil` uses a Windows no-op.
Use that helper for durable rename logic instead of opening directories directly.

### The minors

An older sidecar once accepted a connection but rejected new fields as malformed messages.
Two lanes then retried much faster than healthy lanes and filled neighboring queues.

This incident produced two stable rules:

- Gate network membership on the Contract B version.
- Rebuild every distributed bundle after a protocol change.

A stale value range in an exchanged field can break traffic.
An absent optional field usually removes only derived data.

A game-version mismatch still uses the retained refusal gates.
Do not describe cross-version payload loading as proven.

### Historical deployment evidence

The M3 and M4 development grid provided historical evidence, not current operator state.
Its durable results include:

- 22,595 exactly-once hops across the M3 overnight run.
- A six-world, two-machine M4 grid with active lanes on both axes.
- Route-around and slot reclaim after a hard process stop.
- Periodic save recovery after a game restart.
- Headless game operation without a graphics device.
- One coordinated move to Contract A 2.4 and Contract B 4.0.

The original live readings, resource locations, incidents, and rollout receipts are not part of
this public developer guide.

The original record also contained a seven-step, machine-specific bring-up procedure.
That procedure is historical evidence and is not current public guidance.

### Bringing it back after a reboot

The historical reboot procedure established a stable dependency order.
It checked storage, network forwarding, services, game processes, time scale, and collectors.

Those checks remain useful for a test rig.
Use runtime configuration and current scripts instead of the retired machine-specific values.

### Watch items

Future performance work can repeat these measurements:

- Save-phase duration against raw evolutionary-history size.
- Applied and achieved time scale against population and simulation tick rate.
- Journal compaction size and duration.
- Archive replay rate against current ledger size.
- Forward-receipt cost at real public traffic rates.
- Log and capture retention during long test runs.
- Version-skew behavior across an ordinary game update.

Record the test input, host class, software revision, and measurement window.
Do not present a historical rig value as current service state.

## Gotchas

- Target .NET Standard 2.1. Unity 6 assemblies cannot build against the old 2.0 target.
- Stop the game before plugin deployment. Windows locks the loaded DLL.
- Run Windows interop commands from a Windows-mounted working directory.
- Name each forwarded environment variable in `WSLENV`.
- Map BepInEx logs by content, not launch order.
- If `LogOutput.log` contains required evidence, copy it before a restart.
- Use the readiness flag instead of a fixed sleep before world loading.
- Give every cumulative-ledger assertion a lower time bound.
- Exercise reconnect code by restarting a real component under a live test game.
- Treat M2 and M3 rig scripts as historical until their headers state otherwise.
- Do not infer a populated world from timestamps under `Scenarios/` or `Bibites/Templates/`.

## Useful decompiled entry points

Read [`m1_findings.md`](m1_findings.md) for the full API analysis.

- `ManagementScripts.SaveSystem` serializes, restores, and saves organisms and worlds.
  `LoadBibiteOrEggFromData` restores full live state and preserves the entity identifier.
- `ManagementScripts.GameManager.StartGame` loads a named world without menu interaction.
- `ScriptHelpers.SerializationHelper` reads and writes serialized private fields.
- `ManagementScripts.BibiteTracker` owns the live bibite and egg lists.
- `ManagementScripts.WorldObjectsSpawner.Instance` creates bibites, eggs, and meat piles.
- `SimulationScripts.BibiteScripts.EggHatching.Hatch` is the egg-hatch hook point.
- `SimulationScripts.BibiteScripts.BibiteBody.FixedUpdate` is the border-capture hook point.
- `ScriptHelpers.VersionTracker` and `Utility.Version` implement save-version ordering.

`new Version(0,6,3,3)` selects the alpha overload and means `0.6.3a3`.
It does not mean `0.6.3.3`.
